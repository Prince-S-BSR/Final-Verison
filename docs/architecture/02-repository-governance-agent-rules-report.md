## B. Model Selection Rules

Two independent systems govern model/agent selection, operating at different layers — this is not a conflict (see H.3), but they need to be read together:

**Layer 1 — which subagent for which kind of work** (`CLAUDE.md` "Subagent Model Routing" + the four `.claude/agents/*.md` files):
- **`architect` (Opus)** — schema/data-model design, multi-tenant access-control design, algorithmic logic (dedup/matching/scoring/ranking), migration strategy. "Use sparingly."
- **`implementer` (Sonnet)** — default for CRUD, forms, UI, bug fixes, refactors. The bulk of implementation work.
- **`test-writer` (Sonnet)** — tests, with an explicit priority on multi-tenant/permission-boundary coverage given this is a CRM handling customer PII.
- **`ui-builder` (Sonnet)** — frontend/visual work, told to apply specific skills (below).
- No named agent exists for "research," "security review," or "review" as standalone categories — those fall to whichever of the four above is contextually closest, or to me (the orchestrating session) directly.

**Layer 2 — which decisions require asking a human at all**, regardless of which model executes them (`docs/BMEXA_MASTER_SPEC.md` §88, the "Claude Autonomy Matrix"):
- **May decide unasked**: naming, folder structure, internal helpers, test organization, formatting, minor refactoring, accessibility details, non-functional UI polish, non-semantic indexing, ordinary tooling.
- **Must ask before deciding**: canonical entities, relationships, booking lifecycle, financial logic, CP commission logic, tenant architecture, RLS model, authorization rules, authentication architecture, major dependencies, major infrastructure, offline business behavior, source-of-truth rules, audit requirements.
- **Must never do without explicit authorization**: disable RLS, bypass authorization, expose another tenant's data, use privileged DB access as a CRUD shortcut, silently modify financial history, remove audit controls, weaken authentication, expose sensitive documents publicly, invent business rules, add major future features, silently change the MVP boundary, delete the landing page, replace the application without approval.

**Practical reading**: Layer 1 says *who types the code*; Layer 2 says *what needs your sign-off before anyone types it, regardless of who*. An `architect` invocation for schema work does not itself satisfy Layer 2's "must ask" gate — the last several turns in this conversation (Repository Discovery Report, Architecture Reconciliation Report, this report) exist precisely because Layer 2 requires stopping before Layer 1 execution begins on anything touching entities, RLS, authorization, or authentication.

## D. Delegation Rules

## F. Git Rules

- A `Stop` hook in `.claude/settings.json` runs `git add -A && git commit -m "auto-commit: <timestamp>" ... && git push origin HEAD` after every turn that changes files, unconditionally, no confirmation. This is a **documented, deliberate override** of the Beads block's own Conservative default (`CLAUDE.md`'s "Git Policy Override" section states this explicitly and explains why) — not an unflagged contradiction.
- Pushes always target `origin HEAD` (whatever branch is checked out), never a hardcoded branch name — this repo has stayed on `claude/code-cli-project-init-mgjndj` throughout.
- `docs/BMEXA_MASTER_SPEC.md` §89 asks for "focused branches for meaningful phases/features" and "do not create enormous undocumented commits" — the current auto-commit-per-turn pattern produces many small, timestamp-named commits rather than feature-scoped ones. This is a **real tension worth naming** (§89's spirit is "meaningful commits," the current mechanism produces "every-turn commits") without recommending a change — that's a decision for the project owner, not this report.
